# v0.2.0 — Infraestrutura + Core Transacional e Ingestão

## O que esse release entrega

Fecha os dois primeiros Épicos do projeto: a infraestrutura automatizada
(Épico 1) e o núcleo transacional do serviço de ingestão de trades (Épico 2)
— a metade "escrita" de uma arquitetura EDA/CQRS de clearing.

### Épico 1 — Infraestrutura Automatizada e Contratos de Dados
- Ambiente local via Docker Compose: PostgreSQL 17, MongoDB 8, cluster Kafka
  de 3 nós em modo KRaft, Confluent Schema Registry
- Contrato de dados (`TradeExecutedEvent`) versionado em Avro, com geração
  automática de classe Java no build
- Pipeline de CI/CD (GitHub Actions) com Quality Gate do SonarCloud
  bloqueando merge em caso de cobertura insuficiente ou bugs

### Épico 2 — Core Transacional e Ingestão
- Domínio isolado (DDD/Clean Architecture): `Comprador`, `Vendedor`,
  `Ativo`, `Trade` — zero dependência de Spring/JPA
- Ciclo de vida do `Trade` (`PENDENTE → VALIDADO → LIQUIDADO`/`REJEITADO`)
  implementando Delivery versus Payment: as duas garantias de uma operação
  (saldo do comprador, posição do vendedor) são validadas antes de
  qualquer mutação — nunca uma ponta sem a outra
- Persistência em PostgreSQL via Flyway (schema versionado) + JPA, com lock
  pessimista serializando trades concorrentes contra o mesmo participante
- Publicação de eventos no Kafka via **Transactional Outbox Pattern**,
  resolvendo o dual-write problem entre Postgres e Kafka
- Suíte de testes cobrindo unidade (JUnit 5 + AssertJ + Mockito),
  integração com Postgres real (Testcontainers) e um teste de ponta a
  ponta contra Postgres + Kafka + Schema Registry reais

## Decisões arquiteturais que definem esse release

- **DDD com domínio 100% isolado de framework** — protege as regras de
  negócio (validação de garantia, DvP) contra mudança de tecnologia de
  persistência ou mensageria
- **Outbox Pattern em vez de publicação direta** — garante que "o trade foi
  validado" e "o evento será publicado" nunca ficam inconsistentes entre
  si, mesmo se o Kafka estiver indisponível no momento da transação
- **Lock pessimista em vez de otimista** — serializa concorrência real
  entre trades do mesmo participante, sem exigir lógica de retry no
  cliente

O histórico completo de decisões e trade-offs de cada task está em
[`about/`](.) — um arquivo por task, incluindo o que mudou de ideia no meio
do caminho e os bugs encontrados/corrigidos ao rodar contra infraestrutura
real.

- `trade-query-service` (Épico 3) — módulo Gradle criado, sem código
- Nenhum endpoint HTTP em nenhum dos dois serviços
- OpenTelemetry / correlação de trace entre serviços
